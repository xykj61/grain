**REDS %686 (`20260910.024500`) -- `mantra add` over a file nobody edited wrote a commit anyway, so the record grew with the polling rather than with the work.** *What went wrong:* `cmd_add` in `mantra/src/main.rye` read the file, diffed it against the stored weave, applied the difference, serialized the weave, wrote the commit blob, and moved HEAD -- in that order, unconditionally. On a second run over an unedited file the diff is empty, the weave's bytes are the bytes already on disk so its content-addressed name is the prior name, and `commit_files_with` returns the prior list entry for entry. The commit written from that list records that somebody ran the command. Measured in a pen: three `add` runs over one three-line file left **three commits and three blobs**, and the CLI announced each one as `wove 'a.txt' -- +0 -0 lines. HEAD -> <new>`. *What caught it:* the water rota's cardinal seat, read at this lap's open. Its question is one sentence -- *what did this round change, and would running it again change anything more?* -- and its discipline is taste, which only works up close: build the tool, run it twice, hash the store. Not one of the fourteen guards standing over Mantra had ever run `add` a second time; every one of them proves a **function's** answer or a **record's** shape, and idempotence is a property of neither. *What it taught:* **a store that grows on a no-op is a store whose history has a shelf life.** `cmd_log` walks at most `max_log_depth` commits -- 1,000 -- so a watcher, an editor hook, or an unattended loop calling `add` on a timer pushes the real first commit past the end of the log inside a day, and the part that leaves is exactly the part a version store exists to keep. The tree stated the infusion law in a foundation and proved it in almost nothing; this is what that gap costs in the one module whose whole job is holding history. *Repaired (`20260910.024500`):* `files_agree` compares the list a commit would carry against the list HEAD already carries -- path for path, weave name for weave name, **in order**, since `commit_files_with` builds by walking the prior list and replacing in place -- and `cmd_add` prints `'<path>' unchanged -- nothing to weave. HEAD stays <name>` and returns without writing when they agree. The store's bytes are now identical after the first, second and third run. **CLOSED** by [`../../tools/m/mantra_idempotent_add_witness.rish`](../../tools/m/mantra_idempotent_add_witness.rish) over [`../../tools/fixtures/m/mantra_idempotent_add_scan.sh`](../../tools/fixtures/m/mantra_idempotent_add_scan.sh), which hashes every file under `.mantra/` -- name and content together, since a run that wrote a new blob and left the old ones alone would otherwise read as stable -- and by [`../../tools/fixtures/m/mantra_idempotent_add_control.sh`](../../tools/fixtures/m/mantra_idempotent_add_control.sh), four phases on real builds in a throwaway pen. **The opposite direction is proven as hard as the red**, because a skip is as wrong when it fires too eagerly: `path_only` drops the weave-name comparison and a real edit stops being recorded while a new path still lands; `len_blind` answers yes when the lengths differ and a new file stops being recorded while an edit still lands. Two faults with two cures, told apart by two readings rather than by one. *Not reached:* the document-order seam of `20260910.001500` stands untouched -- a commit that REPLACES a line still sorts out of the document, so this guard's edit leg appends, and it neither tests that seam nor hides it.
