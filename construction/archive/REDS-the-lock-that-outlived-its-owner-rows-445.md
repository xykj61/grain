**REDS %445 (`20260905.231411`) -- the lock that outlived its owner: an empty pid file was read as a lock being born, forever, and every Glow build on this tree waited it out.** *What went wrong:* `lock_acquire` in `tools/fixtures/s/shell_portable.sh` writes the owner's pid INSIDE the lock directory, because `mkdir` is the atomic step and nothing can be written into a directory before it is made. That leaves a window -- microseconds wide -- in which the lock stands and `pid` is empty, and the function was written to wait on that window rather than reap it, since reaping a lock being born hands two holders one lock. The reading is right for a lock being born and wrong for a lock whose owner **died inside that window**: nobody will ever write that pid, and nobody will ever release it. The guard is `[ -s "$_sp_lock/pid" ]`, which is false for a zero-byte file, so the reaping branch below it was never entered and the wait ran to its bound every time. `tools/g/glow_run_worker.sh` passes `BUILD_LOCK_WAIT=1800`, so the price was **thirty minutes per Glow build, on every build, forever**. *What caught it:* the lap's own cold roster, stuck at 96 lines for half an hour. `ps` showed `glow_run_worker.sh src/gate/gate-lantern-face-text-u32.glow 38` at **0.0% CPU** with a `sleep 1` child -- not computing, waiting -- and `stat` read the lock directory's mtime at `17:16:57` against a clock reading `23:02`: **five hours and forty-five minutes**, `pid` zero bytes. The roster's own line then priced it: **`lantern_face green 1454s`** against the **9.5s** its roster row declares, which is **67% of a 2,173-second pass spent on one dead lock**. Nine further Glow guards stood behind it in the roster, each owing the same 1,800s. *What it taught:* **a lock that distinguishes states by presence must distinguish them by TIME, because being born and having died look identical in a single glance.** The comment above the branch stated the correct rule for one of the two states and the code applied it to both, which is why reading the file never found it -- the reasoning was sound and its scope was unstated. The sharper half is what the roster looked like from outside: a guard that declares 9.5s reading 1454s reads as *a slow guard*, and it was a **fast guard waiting on a dead lock** -- the cost landed on the guard's name rather than the lock's, so the number that was wrong pointed at the one thing that was right. *Repaired (`20260905.231411`):* an empty or non-numeric pid file now earns a bounded grace of `grace` consecutive one-second observations -- default **5**, overridable as `lock_acquire <lock> [wait] [grace]` -- and is reaped past it; the counter resets the moment a pid appears, so a lock released and retaken under a waiter's nose is never reaped for its predecessor's silence. The trade is named in the code rather than hidden: the grace opens a microsecond-wide window in which a live owner could be reaped, against a **certain** permanent hang, and every caller already installs through an atomic rename, so a rare double-build leaves a whole binary either way -- safety before speed, TAME's own order. `tools/fixtures/s/shell_portable_control.sh` carries **five new legs**, each run against the elder function first, where **all five miss** (`pass=32 fail=5 verdict=behavior_missed`) and pass against the repair (`pass=37 fail=0`); the seated pair proving a mid-creation lock is waited on keeps both its bounds and both its meanings, since each is shorter than the grace. Both timing legs carry an **upper** bound as well as a lower one, and that is what makes them bites: against the elder the acquire simply failed after its whole 30-second bound, so `elapsed >= 2` and `elapsed >= 4` were trivially true and neither leg could tell the repair from the defect. `tools/s/shell_dialect_witness.rish` GREEN on metal at **27s**, its pin moved 32 -> 37 by a deliberate hand. *Measured after, on the same roster and the same tree one lap apart:* **`lantern_face` 1454s -> 42s** and the whole pass **2,173s -> 800s** -- the 1,412s the guard stopped paying and the 1,373s the pass stopped paying are the same seconds, read from two places. The 42s still stands above the row's declared 9.5s, which was measured on the field Mac `20260830.011217` rather than on this pier; a four-fold difference between two machines is ordinary and is named here rather than resolved, since nothing in this round measured that row on the bench it was written on. *Booked three times before it landed:* `--next` read 439 at 23:07, 442 after the first rebase, and **444** after the second, as three seats booked five rows in one hour -- a published number never moves, so the unshared row moved instead, six citations with it each time. **Fetch-before-book is a reading that goes stale at the speed of the fleet, rather than one act at the open.** **CLOSED.**
