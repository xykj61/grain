# REDS %427-%429 -- the room the instrument was standing in

*Folded from the living pin [`../REDS.md`](../REDS.md) on `20260905.152212` to bring it back
under bound as `%430` and `%431` landed, three rows written inside one hour by two ships. What runs through them is an answer
that was true of the room the instrument could reach and false of the room anyone was asking
about: a jail that bound one tree while the keys it needed sat in a sibling, a round-open that
reported a clean tree while a rebase stood over it, and a `%G?` reading `N` for a `gpg` that failed
to exec rather than for a commit that was never signed. None of the three misreported what it saw.
Each was pointed at somewhere slightly beside the question. Link depth moved with the text.*


**REDS %427 (`20260905.150047`) -- one jail binds one tree, and pheromone's keys were in another.** *What went wrong:* `grain-pheromone`'s `.git/config` named `gpg.program` at `/home/keeper/grain-petrichor/.gnupg-rye/gpg.sh`, and its `.git/ssh_config_jail` named every `IdentityFile` and `UserKnownHostsFile` inside `grain-petrichor/.ssh`. The tree owned **no `.gnupg-rye` and no `.ssh` at all**. `agent-jail.sh` binds exactly ONE tree into the enclosure, so from inside its own jail pheromone could neither sign a commit nor open an ssh connection -- while every check run at a host prompt passed, because at a host prompt the sibling is right there. *What caught it:* the pheromone seat itself, from inside the wall, reporting it as a custody ask rather than working around it. *What it taught:* **two decisions, each correct alone, can be incompatible.** `birth_a_clone.rish` copied the field's absolute key paths on purpose -- its own comment reads *host-shared custody material behind per-clone config, so every newborn signs as the one keeper* -- which is sound thrift on a single-tree pier and unrunnable under a one-tree-per-jail enclosure. Neither rule was wrong; nothing owned the seam between them. And the fault sat where no standing guard could reach: `.git/config` and `.git/ssh_config_jail` are **untracked by design**, so `tracked_link_scan`, the commit hook's path check, and the link duty are each blind to them by construction. *Repaired (`20260905.150047`):* pheromone owns its own `.gnupg-rye` and `.ssh`, holding the same keys it already named, so no trust relationship changed and only reachability did; all three shims now resolve `GNUPGHOME` from their own `$0`, so a copy is correct in whatever tree it lands in; and `birth_a_clone.rish` copies the keyring and the ssh material into the newborn, rewrites the copied config's paths from field to newborn, and **refuses if the field's name survives the rewrite**. Proven: pheromone signs and reaches `xy` entirely from its own paths. Gated by `tools/f/fleet_key_locality_witness.rish` over `tools/fixtures/f/fleet_key_locality_scan.sh` -- **16 paths across 3 trees, foreign_paths=0** -- with 13 control legs on real repositories in a pen, the foreign path planted and then removed so the refusal is proven from both sides, an absent tree reported rather than counted, and the scan refusing loudly when its own roster is missing. **CLOSED.**

**REDS %428 (`20260905.150047`) -- the round-open reported a clean tree over a standing rebase.** *What went wrong:* `tools/f/fleet_round_open.sh` runs `git reset --hard xy/main` on every live fleet tree at every round-open, and modeled no interrupted rebase. All three of its later steps misread one: a conflicted worktree reads dirty, so the stash step stashed a half-replayed commit; HEAD is detached at whatever was replayed last, so the classifier answered about a commit nobody asked about; and the reset then abandoned the rebase mid-flight, leaving the real branch behind and unnamed. *What caught it:* the pheromone seat, which opened mid-rebase and said so, asking that the round-open refuse rather than continue. *What it taught:* **a script with no control was resetting live trees every twenty minutes.** Running its own first control against the elder script showed the failure exactly: on a real conflicted rebase the elder printed `already on the anointed order` and `open on 45c9c0fd26` -- a healthy open, reported over a corpse -- which is the same tail-reading class the script's own header was written to close, firing one state deeper than the header reached. A file that documents its own past misreports this carefully is a file worth giving a control. *Repaired (`20260905.150047`):* the corpse is cleared before anything else reads the tree -- the pre-rebase tip is parked by name out of `orig-head` first, then `git rebase --abort` restores the exact pre-rebase branch and HEAD, which is git's own guarantee, so no committed work is lost; a rebase that will not abort exits 2 and asks for a hand rather than resetting. The honest limit is written at the site: conflict resolution staged but uncommitted inside the rebase is not preserved and no script can preserve it, which is acceptable only because the fleet law is one writer per checkout. `tools/fixtures/f/fleet_round_open_control.sh` proves **14 legs** on real repositories with a real anointed remote and a real conflicted rebase, and **fails 5 of them against the elder script**. **CLOSED.**

**REDS %429 (`20260905.151609`) -- `N` from `%G?` means gpg failed as often as it means unsigned.** *What went wrong:* the pheromone seat read `git log --format=%G?` on its own tree, saw `N` on the last five commits, and reported the tree as unable to sign. The commits were signed the whole time -- the raw objects carried `gpgsig` on all eight it checked. `N` was gpg **failing to exec**, because `gpg.program` named a wrapper inside a sibling tree the jail does not bind (REDS %427). *What caught it:* the seat checking the raw object after the summary field disagreed with its expectation, and writing the correction down rather than accepting the first reading. *What it taught:* **a status field that collapses `could not check` into the same letter as `is not signed` will be read as the more alarming of the two.** git actually distinguishes them -- `N` unsigned, `E` cannot check, `U` good from an uncertified key, `G` good -- yet a tree holding only its own public key returns `E` for every peer's commit, and `E` at a glance reads like `N`. So the ambiguity was not in git; it was in a fleet where no ship could verify another. *Repaired (`20260905.151609`):* the fleet's public keys are cross-imported into all three keyrings with ownertrust seated -- **public material only, no secret key moved, no custody touched** -- and all three trees now read `GGGGGGGG` across their last eight commits where two of them read `E` and one read `N`. `birth_a_clone.rish` carries this forward for free, since it copies the field's whole keyring into a newborn. The scan `tools/fixtures/f/fleet_key_locality_scan.sh` reports each tree's key count as a **reading rather than a gate**, because a ship missing a peer's public key still signs and pushes perfectly. **CLOSED.**
