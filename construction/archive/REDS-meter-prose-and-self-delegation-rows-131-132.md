**REDS %131 (`20260822.055523`) -- the meter's prose was edited after the choir sang, and a red shipped inside a commit that claimed green.** *What went wrong:* the previous lap closed REDS %130 by building the widening meter, then wrote `(REDS %130)` into two `say` lines of `tools/ca/caravan_ladder_carry_witness.rish` so a reader would find the row from the meter. The Caravan choir had already sung by then. `tools/fixtures/caravan_ladder_prose_count_scan.sh` reads every digit run in a meter's `say` lines and refuses any not held by an `assert` in the same file, so the bare `130` inside the citation reddened `caravan_ladder_copy_witness.rish` -- and through it the whole suite of one hundred and eight. The commit shipped signed with a session log claiming the choir GREEN. Both halves were true when measured and false when sent. *What caught it:* running the suite at the head of the next lap before touching anything, and then checking whether the red belonged to this lap's own edit -- `git stash` and rerun proved the tree was already red at HEAD. *What it taught:* **a witness proves the tree it ran on, so any edit after the run reopens the claim.** A meter's prose is part of the meter; adding a sentence to it is a change like any other, and the choir sings after the last edit rather than before the last thought. The deeper fault is the guard's own bound: `%` is the sigil this tree assigns to a number it names itself, marking a constant term that is exactly itself and never varies (`.claude/rules/git-signing.md`), and a ledger row is immutable by the ledger's own first law -- so a `%`-sigilled citation can never drift, which is the only fault that scan exists to catch. A gate that reds on valid input teaches a bench to route around it, and this one had begun to.

**REDS %131 CLOSED (`20260822.055523`) -- the sigil reads as a name, and both directions run on a control.** *The repair, on metal:* `tools/fixtures/caravan_ladder_prose_count_scan.sh` strips `%<digits>` from a `say` line before extracting any number, so a citation of this tree's own ledger passes as the name it is while every bare count beside it stays refused. The bound is deliberately tight -- only a digit run wearing the sigil is exempt, so the exemption is a name rather than a doorway. `tools/ca/caravan_ladder_copy_witness.rish` proves both directions on one generated control: a meter whose only numbers wear the sigil reads `LADDER_PROSE_COUNT_OK`, and the same meter with one bare `47` beside those citations is refused by that count named at its own value. The controls themselves went wrong once and were caught the same way -- `printf` reads a bare `%` as a format conversion and truncated the whole generated line, so both legs passed while testing an empty sentence, the welcome for having nothing to refuse and the refusal for having no count left to find. The sigil is written `%%` in the fixture now, and the refusal leg failing is what found it. The two real citations in the carry meter's prose stand unchanged, and this lap's own counts are spelled in words as the rest of that file's prose already spells them.

**REDS %132 (`20260822.074425`) -- the lift's own stub loop kept eating the harness it had just written, and three laps caught it by hand.** *What went wrong:* a lift moves one byte-identical function body into `caravan/ladder_checks.rye` and rewrites every rung that wrote that body into a three-line stub calling it. The rungs are found by globbing `caravan/*.rye` for the family name -- and `caravan/ladder_checks.rye` lives in that same directory, so the moment the harness receives the body it also matches the glob, and the loop replaces the body it was just given with a stub calling itself. This lap it happened again, on `redress_the_meeting`: the fold loop reported seventeen rungs where sixteen were expected, and the harness stood holding `return ladder_checks.redress_the_meeting(@This(), ...)` where its lifted body belonged. *What caught it:* the count disagreeing with the meter. `REACH_OK` had named `folding=16` before a line moved, the loop printed seventeen, and reading the harness confirmed it. Caught before any build, so nothing shipped. *What it taught:* **this is the third firing of one lantern, and the first two were each repaired by hand and written into a log rather than into a tool.** The `say_the_word` lap recorded a glob overwriting the harness with its own stub; the `meet_the_debt` lap next to it wrote that its stub loop *excluded the harness by name this time rather than by luck* -- naming the fault exactly and leaving the tree with no check that would notice the fourth time. A lantern that fires twice becomes a loom, and this one fired three times in one arc. The fault is unambiguous on disk and free to read: the harness delegating to itself is a shape that can never be correct.

**REDS %132 CLOSED (`20260822.074425`) -- a harness that delegates to itself is refused by name, on the roster that already runs every lap.** *The repair, on metal:* [`tools/fixtures/ladder_stub_length_scan.sh`](../tools/fixtures/ladder_stub_length_scan.sh) greps `caravan/ladder_checks.rye` for a line whose body is `return ladder_checks.` and refuses with `verdict=harness_delegates_to_itself`, naming the file, before it measures anything else. The check sits ahead of the measurement deliberately, since a clobbered harness still leaves every rung's stub intact and would otherwise answer `verdict=ok` about a tree that no longer compiles. [`tools/l/ladder_stub_length_witness.rish`](../tools/l/ladder_stub_length_witness.rish) asserts the refusal alongside the two it already proved, and the control is a throwaway ladder holding one self-delegating function, so the living harness is never touched to prove the guard. That witness is rung ten of the era suite, which runs at the head of every lap of this arc, so the fourth firing is a red the bench reads rather than a shape a hand happens to notice.
