**REDS %262 (`20260826.090745`) -- the agent measured through a shell whose `grep` was not the scripts' `grep`.** *What went wrong:* checking whether a portable byte range could replace `grep -P`, the reading came back `0` on a file that plainly carried high bytes, and a first pass read that as GNU grep refusing a bracket range in the C locale. It was not GNU grep. This bench's interactive shell defines `grep` as a **function wrapping ugrep 7.8.4**, while a tracked guard invoked as `sh tools/fixtures/...` gets `/run/current-system/sw/bin/grep`, **GNU grep 3.12**. Under the real one the range and the PCRE read identically. A whole-tree parity check taken the same way read 26,817 references where GNU reads 35,642. *What caught it:* `type grep`, asked because the reading disagreed with the documentation -- and `sh -c 'command -v grep'`, which answers for the environment the subject actually runs in rather than the one the question was typed in. *What it taught:* **measure through the shell the subject runs in.** An agent's own shell is an environment like any other, and a wrapper, alias, or function in it silently changes what every reading means. This is REDS %174's family -- a green that measures a different tree than the one that ships -- reaching the bench rather than the index. The habit is cheap: run a measurement inside `sh -c` when the thing being measured is a script. *Repaired:* every reading in the round retaken under `sh -c`, and the parity proof re-run under GNU grep, where the two spellings agree byte for byte across 35,642 references. CLOSED.
