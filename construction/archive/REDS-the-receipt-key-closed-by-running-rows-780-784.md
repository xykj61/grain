# REDS %780, %784 -- the receipt key's two halves, each closed by running rather than reading

*Folded from the living pin [`../REDS.md`](../REDS.md) on the lap that closed the second of them.
The pin stood at 66,487 of the 65,536 its own header declares -- 951 bytes over, with seven closed
rows foldable -- and these two came first because they are one arc: `rye/src/main.rye`, the build
receipt's key, and the same lane.*

*What they teach together. The first half asked whether a receipt is POSSIBLE before paying for
one, moving four cheap conditions ahead of a 172MB read; the second half read the compiler's bytes
once per compiler rather than once per keyed build. Neither fault was found by reading the code.
`%780` was found by RUNNING a refusal on a path nobody runs, and by MUTATING a repair to see
whether any leg objected -- none did. `%784` was found by running the control a design paper cited,
against a binary built from the source that paper described; the paper had already recorded six
mutations planted one at a time, and one of the five comparisons it named did not exist.*

*The clause worth carrying forward, in two lines. A member of a conjunction is proven only where
every other member would have let it fail -- so a leg over a compound condition proves the first
clause that refuses and says nothing about the rest, while reading exactly like coverage. And a
proof WRITTEN rather than run reads exactly like a proof. The cure is the same in both: plant the
mutation, watch something object, and lift it.*

---


**REDS %780 (`20260916.193716`) -- a condition never exercised alone is a condition never proven, and both halves of one conjunction were asleep.** *What went wrong:* `rye/src/main.rye` decides a build receipt from a conjunction of conditions, and two of its members stood unread for different reasons. **First, a refusal named a cause it had never looked at.** `unkeyable_reason` walked four readings and asserted they were exhaustive once an output was named; `RYE_BUILD_FRESH` was a fifth, and it was not a reading at all. So `RYE_BUILD_FRESH=1 rye key <file> -femit-bin=<out>` answered `this binary's own path could not be resolved, so its bytes cannot join the key` -- false in every part, about a path that resolves perfectly well, sending an operator to hunt a healthy binary. **Second, the guard family's own leg for the `run` exclusion exercised a different condition entirely.** Leg 14 of `tools/fixtures/r/ryekey_control.sh` invokes `run` with no emit flag, so the no-output condition refuses the receipt first and the `run` clause beside it is never under test. Proven by planting: deleting the run exclusion outright left all 24 legs GREEN. What that misses, shown on metal, is the worst shape this family can fail in -- with the exclusion gone, `rye run <file> -femit-bin=<out>` earns a receipt on its first call and HITS on its second, and a hit emits nothing and spawns nothing, so the second invocation **printed nothing and exited 0**. A `run` that does not run, reporting success. *What caught it:* the fire rota row, read by its own instruction -- look straight at the uncomfortable point rather than around it. Neither fault was found by reading the code. The first was found by RUNNING the refusal on a path nobody runs, and the second by MUTATING the repair to see whether anything objected; nothing did. No instrument could have caught either, because both are conditions inside a conjunction that no leg isolates, and a conjunction passes whole. *What it taught:* **a member of a conjunction is proven only where every other member would have let it fail.** A leg that exercises a compound condition proves the first member that refuses and says nothing whatever about the rest, and it reads exactly like coverage. The cure is per-member isolation rather than a further leg over the whole: leg 20 names the bypass's own sentence, leg 21 proves an unkeyable flag is blamed on the flag rather than on a file the skip never opened, and leg 22 gives `run` an output to name so the exclusion is finally the reading under test. All three were proven to BITE by planting the mutation and lifting it, since a leg proven only in the passing direction cannot be told from a bypass. **And the second fault was created by this lap's own repair being safe:** moving the run exclusion into a single cheap predicate gave it exactly one home, which is what made a one-line deletion survivable and therefore worth planting. A repair that consolidates a condition owes that condition a leg. Both instances repaired, three legs added and each proven to bite by planting the mutation and lifting it; `ryekey` GREEN on metal at 25 legs. **CLOSED.**

**REDS %784 (`20260916.204153`) -- a paper claimed six mutations it could not have run, and one of the five comparisons it named did not exist.** *What went wrong:* `digest_record_read` in `rye/src/main.rye` computed `seen_path` and never read it. The remembered-digest record carries five identity readings -- path, inode, size, mtime, ctime -- and the function refused a record on four of them. A record whose `path` line named a different file was trusted, and its digest went into the build key. The design paper standing beside the work, `active-designing/date/20260916/20260916-202830_the-compiler-read-once-rather-than-once-per-build.md`, said each of the five readings was refused by its own plant, and said plainly that *six deletions were made in `rye/src/main.rye`, one at a time -- the record read itself, and each of the five identity comparisons -- and the control was run whole against each mutated binary.* That account cannot be true of a comparison that was never written. *What caught it:* running the control the paper cites, against a binary built from the source the paper describes. `tools/fixtures/r/ryekey_control.sh` leg 28 corrupts each field alone, and it answered `RED: a record whose path disagreed with the file was trusted` on the first honest run. Two doors had to open before it could speak: the binary on this pier was built from an elder source carrying the **same** `rye_version`, so the control's own staleness door read `stands at or past its source` and waved a binary through that behaved differently -- a behavior change that moved no version stamp. *What it taught:* **a written proof is a claim like any other, and the run is what settles it.** Planting a mutation proves a leg bites; writing that a mutation was planted proves nothing at all, and reads identically. The prose here was not dishonest -- it was a lap recording the shape it had designed rather than the shape it had built, which is the ordinary way this fault arrives. The companion lesson is the staleness door: `rye_version` is the one reading that tells a binary from its source, so **a behavior change in that file moves that stamp**, and the doc comment beside it now says so where a reader edits. Repaired: `if (!seen_path) return null;` seated with its reason, `rye_version` moved to this lap's stamp, and the paper's proof section rewritten to the account that actually ran. `ryekey` GREEN on metal at 30 legs. **CLOSED.**
