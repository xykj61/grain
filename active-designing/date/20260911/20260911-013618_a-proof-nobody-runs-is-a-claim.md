## The first draft read zero, and was wrong

Both elder naming rules end `\.(rish|rye)`. Run the closure's own rule over the heard set and ask it
for controls and it answers `control_heard=0` -- a clean, quotable, entirely false number, since a
`.sh` path cannot match either pattern. A plain `git grep` of the same tree says 248 of 258 controls
are named somewhere.

**A rule is paired with the population it can see, or it reads zero and calls it news.** The
third reading carries its own rule for that reason, and the tree already knew it: the wide naming
rule exists because the narrow one reads past its own second population, and says so in its header.

## Why a ratchet

The law here is *a gate that reds on ordinary work is a gate somebody turns off*. A wall at zero
would ask a hand to roster eighteen guards in one lap, so the ceiling opens at 18 and only falls.

It also holds still under ordinary growth, which is what makes the ratchet honest as well as
workable: a control arrives beside the witness that runs it, so a new pair joins `heard` on the lap
it lands. The number moves when something is left behind, and only then.

## What it does not reach

**Whether a control that runs proves anything.** This counts who is listening. The tree keeps a
separate reading for a leg that always passes, and that stays its own question.

**The scans.** `tools/fixtures/` holds hundreds of `*_scan.sh` beside these controls, and a scan
nothing runs is a different shape -- a scan is reached through the witness that reports it, where a
control is reached only by being executed. That reading is named here and left for its own lap.

*May every proof this tree writes be run by something, so the day a reading drifts, a leg is there
to hear it.*
