# secp256k1 ECDSA public-key recovery — reading the sender back out of a signature

## The claim

With the secp256k1 tower proven end to end — base field, group law, scalar
ladder, scalar field mod n, and ECDSA both **verify** and **sign** all GREEN —
one operation still separates the library from the whole Ethereum account model:
**recovery**. A verifier is handed a public key and checks a signature against it;
recovery is handed only a signature and reads the public key *out* of it. This is
the `ecrecover` primitive — the EVM precompile at address `0x01` — and it is the
Lindy crux of the tower, because the sender of every Ethereum transaction, every
Sign-in-with-Ethereum session, and every EIP-191/712 authenticated message is
*defined* as the address of the key recovery returns. This rung authors it in pure
Rye, composing only GREEN rungs and adding exactly one new piece of base-field
arithmetic — a square root.

## The mathematics — SEC 1 §4.1.6 recovery

Given a signature `(r, s)`, a message hash `z`, and a one-bit recovery id:

1. Refuse unless `r` and `s` both lie in `[1, n−1]` — the same range gate verify runs.
2. Take `R`'s x-coordinate to be `r`. Because `n < p` for secp256k1, every `r` in
   `[1, n−1]` is already a canonical base-field element, so no x-overflow case can
   arise in the Ethereum domain. The overflow ids `2` and `3` (SEC 1's `j = 1`,
   `x = r + n`) fall outside Ethereum's `v = 27/28` and are refused — exactly as
   the EVM precompile refuses anything but `27` and `28`.
3. **Decompress** `R`: solve `y² = x³ + 7` for `y`, and pick the root whose low
   bit matches the recovery id. This is the one new arithmetic (below).
4. Fold `z` to a scalar mod `n`; compute `r⁻¹ mod n`.
5. Recover `Q = r⁻¹·(s·R − z·G)` over the GREEN complete group law and ladder —
   the two points `s·R` and `z·G` subtracted, then scaled by `r⁻¹`. That `Q` is
   the public key that signed.

Recovery is verification run backward, and it uses no operation the verifier
lacked but one: turning an x-coordinate back into a point.

## The one new arithmetic — a base-field square root

Decompression needs `√(x³ + 7)` in the base field. secp256k1's prime satisfies
`p ≡ 3 (mod 4)`, which gives the closed form `√a = a^((p+1)/4)` whenever `a` is a
quadratic residue: no Tonelli-Shanks, just a single fixed exponentiation. The
exponent is a public curve constant,

```
(p+1)/4 = 2²⁵⁴ − 2³⁰ − 244
        = 0x3FFFFFFF_FFFFFFFF_FFFFFFFF_FFFFFFFF_FFFFFFFF_FFFFFFFF_FFFFFFFF_BFFFFF0C
```

walked most-significant-bit-first by the **same square-and-multiply ladder**
`fe_secp256k1.rye`'s inverse already uses for `a^(p−2)`. The result is verified —
`β² = x³ + 7` — before it is trusted, so a non-residue `x` (an `r` that lies above
no curve point) returns `error.NoPoint` rather than a wrong `y`. The two roots are
`β` and `p − β`, of opposite parity; the recovery id's low bit chooses between
them, and `p − β` is computed as `0 − β` through the GREEN field subtraction.

## Custody — recovery is non-gated

Unlike signing, recovery touches **no secret**. Every value it reads — `r`, `s`,
`z`, the recovery id — and the value it returns — the public key — is public by
construction; recovery *reconstructs a public key from public data*. So the
variable-time square root, inversion, and ladder leak nothing that is not already
public, and this rung sits with verification on the non-gated side of the library.
It answers *who signed this?*, never *sign this*: signing a record with the
maintainer's own identity key stays the custody gate (#3/#4), untouched by this
rung.

## The witness — two independent references

`tools/crypto_secp256k1_ecrecover_witness.rish` asserts the `GREEN
crypto-secp256k1-ecrecover` line against two references runnable today:

- **An algebraic round-trip.** For each of Zig's deterministic key pairs, the
  `(r, s)` it signs recovers back to *exactly that public key* at exactly one
  recovery id, and the other id does not return it; a one-bit tamper of the hash
  recovers a different key; and the recovered key's Ethereum address, through the
  GREEN `eth_address.rye`, matches the key's own — the full `ecrecover → sender`
  chain, end to end.
- **Zig's independent decompression.** Our authored base-field square root is
  checked against Zig's `std.crypto.ecc.Secp256k1.fromSec1` byte-for-byte on
  `R`'s recovered y, across eight deterministic keys — so the one new arithmetic
  has its own direct, independent witness rather than resting only on the
  round-trip.

Registered in `crypto_suite_witness.rish` after `eth_address` — the composition it
demonstrates — so the count guard's bijection stays whole at thirty-eight files.

## Why this rung is the Lindy crux

secp256k1 verify and sign prove the library can *check* and *make* Ethereum
signatures; recovery is what makes those signatures **addressable**. It is the
foundation the Dimeroll receipt (a Kumara login against an Ethereum key), the
Comlink peer's claim, and any future EVM-facing surface all stand on — one
primitive, serving every module that will ever ask *who signed this?* rather than
one. That is exactly the double-seat's test for a durable thread: it serves the
whole tree, not a single lap.

*May the sender we read back out of a signature be the very one who wrote it, and
may every key we recover in the open resolve to the hand it truly belongs to.*
