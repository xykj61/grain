## The claim

With the secp256k1 base field, group law, scalar-multiplication ladder, and the
scalar field modulo the group order **n** all GREEN, **ECDSA verification** is now
a pure composition over them — no new cryptography, only the assembly the whole
secp256k1 tower was climbing toward. This rung authors
[`crypto/secp256k1_ecdsa.rye`](../crypto/secp256k1_ecdsa.rye): given a public key
`Q = (Qx, Qy)`, a message hash `z`, and a signature `(r, s)` — all in the
ecosystem's big-endian byte convention — decide whether the signature is valid,
by the exact SEC 1 verification equation.

## The equation, step by step

1. **Range gate.** Reject unless both `r` and `s` lie in `[1, n−1]` — the
   `is_canonical` below-n check from the scalar field, plus a non-zero test.
2. **Hash to scalar.** `z = hash mod n` — the same reduction Zig's verifier runs
   (`reduceToScalar`), a big-endian value folded mod n. Reject if `z` is zero
   (faithful to the reference).
3. **Inverse.** `w = s⁻¹ mod n` by the scalar field's Fermat inversion.
4. **Two scalars.** `u1 = z·w mod n`, `u2 = r·w mod n`.
5. **The point.** `R = u1·G + u2·Q`, over the GREEN ladder and complete group law.
   Reject if `R` is the point at infinity (Z = 0).
6. **The check.** Accept iff `affine_x(R) mod n == r`.

## On-curve gate — one honest strengthening beyond the reference

Zig's verifier assumes a well-formed `PublicKey` (its `fromSec1` validates
on-curve at construction, outside `verify`). Because this rung takes affine
coordinates directly, it adds its own **on-curve check** — `y² == x³ + 7` in the
base field — and rejects a public key that does not satisfy the curve equation.
This is audit discipline: a verifier that trusts an off-curve key trusts nothing.

## Byte order — the one product with the outside world

The ecosystem encodes `r`, `s`, hashes, and coordinates **big-endian**; the scalar
field and the ladder walk **little-endian**. The reversal is this file's boundary
courtesy — the same seam every secp256k1 rung named — never the arithmetic's
concern.

## Parity — two witnesses runnable now

- **Algebraic known-answers anyone can check:** a Zig-produced signature verifies
  true; a one-bit tamper of `r`, `s`, `z`, or a coordinate is refused; an
  all-zero `r` or `s` is refused (out of range); an off-curve public key is
  refused; and the classic **malleability fact** — `(r, n−s)` verifies exactly
  when `(r, s)` does — holds.
- **Independent implementation:** for a spread of deterministic key pairs and
  messages, our verdict equals Zig's own
  `std.crypto.sign.ecdsa.EcdsaSecp256k1Sha256` verify, true-for-true and
  false-for-false. secp256k1 is not in Monocypher, so the two witnesses are the
  algebraic answers and Zig's `std.crypto` — never a copied line.

## Honest scope

Software only, purely local — no network, no funds, no real device, no identity.
Every value ECDSA **verification** touches — `r`, `s`, `z`, the public key, the
inverse — is **public**, so the variable-time arithmetic leaks no secret; that is
the whole reason verification is the non-gated rung. ECDSA **signing** with a real
private key stays the custody gate (#3/#4): the agent builds and proves the
verifier; the key stays the maintainer's hand. Constant-time signing arithmetic
remains the Season's named horizon.

## Why this rung, now

Verification unblocks every module that must *check* a secp256k1 signature —
Kumara identity against an Ethereum/Bitcoin key, a Dimeroll receipt, a Comlink
peer's claim — without holding a key. It is the highest-Lindy, still-tractable
move on the secp256k1 tower, and it finishes the arc the Keccak-256 · RIPEMD-160 ·
Base58Check · Bech32 · EIP-55 address work began.
